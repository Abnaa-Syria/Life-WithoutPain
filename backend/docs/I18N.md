# Backend API Internationalization (i18n)

## Locale resolution order

1. `User.preferredLanguage` (when authenticated)
2. `Accept-Language` request header
3. Default: `en`

Resolved locale is exposed as `req.locale` and via `AsyncLocalStorage` (`getLocale()`).

## User preferred language

- DB default for new users: `ar`
- Canonical update: `PATCH /api/v1/auth/preferred-language` with `{ "preferredLanguage": "ar" | "en" }`
- Settings/profile PATCH paths still accept `language` / `preferredLanguage`

## API messages (errors & success)

- Response shape unchanged: `{ success, message, errorCode, data?, errors? }`
- `errorCode` is stable and language-independent (e.g. `INVALID_OTP`, `PATIENT_PROFILE_NOT_FOUND`)
- `message` is localized from JSON catalogs under `src/i18n/locales/{en,ar}/`
- Throw errors with codes: `throw new UnauthorizedError('INVALID_CREDENTIALS')`
- Success responses: `successResponse(res, { messageKey: 'LOGIN_SUCCESS' })`

### Adding a new error code

1. Add to `src/i18n/errorCodes.js` (HTTP status)
2. Add keys to `locales/en/errors.json` and `locales/ar/errors.json`
3. Throw using the code in services/middleware

## Validation

Zod uses message keys (e.g. `INVALID_PHONE`). `validate` middleware maps issues to `{ field, messageKey, params }`; `errorHandler` translates them.

## Business content (translations table)

Multilingual catalog/content uses `entity_translations`:

| Column | Description |
|--------|-------------|
| entityType | e.g. `speciality`, `service`, `notification` |
| entityId | PK of the entity |
| locale | `en`, `ar` (extensible) |
| fieldKey | `name`, `description`, `title`, `body`, `category`, `bio` |
| value | Text |

### API shapes (breaking change)

**Patient/doctor/public reads** — localized fields for `req.locale`:

```json
{ "id": 1, "name": "Cardiology", "description": "..." }
```

**Admin reads/writes** — full payload:

```json
{
  "id": 1,
  "translations": {
    "en": { "name": "Cardiology" },
    "ar": { "name": "..." }
  }
}
```

Legacy `nameAr` / `nameEn` columns were removed. Admin may still POST legacy fields; they are normalized into `translations`.

### Registering a new translatable entity

1. Add to `src/i18n/translatableEntities.js`
2. Use `TranslationRepository.upsertSet` on create/update
3. Use `attachTranslations` / `mapEntityForApi` in list/detail endpoints
4. Search via `TranslationRepository.findEntityIdsBySearch`

## Enums, dates, numbers

- Enum values remain UPPER_SNAKE_CASE (never localized)
- Dates/amounts in API are ISO strings and numbers; clients format for display
- Dashboard charts use `periodStart` + `count` / `amount` (no locale-formatted labels)

## Client responsibilities

- Send `Accept-Language: ar` or `en`
- Branch on `errorCode`, not English `message` text
- Format dates, numbers, and currency in the UI

## Database migrations

After pulling i18n schema changes, apply pending migrations (avoids `migrate dev` reset when a past migration file was edited):

```bash
npm run db:migrate:apply
npm run db:seed
```

Use `npm run db:generate` after **stopping the running API server** (Windows may lock `query_engine-windows.dll.node` with EPERM otherwise).

If `prisma migrate dev` asks to reset because a migration was modified after apply, prefer `npm run db:migrate:apply` on existing databases, or `npm run db:reset` only when a full dev reset is acceptable.
